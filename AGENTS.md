# Coding-agent instructions — Pizza Dough Calculator

These are standing instructions for `hound83/pizza-dough-calculator`. The user's current task determines the deliverable; these rules safeguard the product and how an agent completes work.

## Outcome ownership

- Deliver a **complete, meaningful milestone** for substantial implementation requests. Do the necessary research, code, integration, regression repair, responsive/browser checks and relevant documentation together. Do not stop after the first patch to ask whether to perform obvious in-scope follow-ups. Respect explicitly narrow fixes instead of adding unrelated scope.
- Establish the expected outcome, baseline, non-goals and testable completion conditions. If the user does not know exact acceptance thresholds, derive evidence-based provisional criteria and proceed, except for a material product decision.
- Do not expand into unrequested algorithm recalibration, storage redesign, feedback services, or refactors. Record tangent findings for later. Diagnosis/review-only requests are read-only.
- Stop only when the milestone is verified, a genuine decision/access blocker arises, or runtime limits intervene. If interrupted, leave reproducible state and the precise remaining next step.

## Sources of truth and architecture

- Inspect current git status, remote branch/PR state when available, `README.md`, and only relevant files. Read `docs/PRODUCT_GUARDRAILS.md` for any behavior/calculation change; `docs/ARCHITECTURE.md` for module, entrypoint or storage work; `CONTRIBUTING.md` for contribution and localization rules. Do not reread all three completely for a trivial unrelated edit.
- The modular source is under `src/`. The root `index.html` is generated by `npm run bundle` and serves GitHub Pages; **never edit generated root `index.html` directly**. Commit required regenerated artifacts alongside their source.
- Historical release/review notes (including older `CLAUDE.md` sections) are evidence of past versions, not automatically current release instructions. Prefer the current `README.md`, explicit decisions and live branch state.

## Non-negotiable product behavior

- `docs/PRODUCT_GUARDRAILS.md` is authoritative for immutable product contracts. Never silently change golden hashes or rewrite accepted historical baselines to satisfy a test.
- Preserve the calculation, fermentation, temperature and AVPN contracts defined in `docs/PRODUCT_GUARDRAILS.md`, including the distinction between practical guidance and scientifically validated measurements.
- Preserve Dutch and English coverage, Basic/Full behavior, recipes and per-pizza identity, checklist state, active evening/batch chronology, cross-tab ownership, share-link privacy, and local persistence unless the authorized feature changes them.
- A storage-schema change needs a documented migration and regression tests. A numerical/functional contract change needs explicit product authorization, focused tests, versioning rationale and a documented new baseline; never sneak it in as cleanup.

## Implement → validate → improve

1. Capture a reproducible before-state, especially for calculations, persistence and affected user journeys.
2. Implement in maintained source modules. Run `npm run bundle` and `npm run check:bundle` to ensure the website entry is current.
3. Run `npm test` before claiming completion. Use `npm run test:fast` only for intermediate feedback, not as a substitute for the final full suite.
4. When UI or workflow changes, exercise the real site in Chromium/Playwright where available, including mobile viewports, both languages, keyboard/touch paths, saved-state recovery and relevant migration/restore cases.
5. Inspect numerical outcomes, failed tests and unexpected UX; repair in-scope issues and rerun. A green regression suite does not itself prove that a new baking model is physically accurate.

## Git, autonomous publication and reporting

- Use a feature branch and reviewable PR for substantial work. Preserve `main`, release records and user changes. Do not force-push or directly replace accepted baselines.
- **Standing owner authorization:** for an authorized implementation milestone, autonomously **merge the verified PR and publish through the repository's established GitHub Pages flow** once all relevant release gates are met. Do not apply this to review-only requests or unrelated changes.
- **Required gates:** the approved user journey/acceptance checks are complete; `npm run bundle`, `npm run check:bundle` and the full `npm test` pass; required GitHub CI checks pass on the exact PR revision; relevant Chromium/Playwright workflows, both languages, mobile and keyboard paths have been checked; numerical guardrails, saved data, migrations and share-link/privacy boundaries are preserved or explicitly and safely changed; no release-blocking issue or unapproved change remains. Inspect the diff and retain a rollback path.
- Respect branch protection, required reviewers, permissions and deployment approvals. If a check or required review cannot be obtained, **stop before merge** with a tested PR and the precise blocker; never bypass it or silently rewrite golden hashes.
- After merging, verify the deployed **live** calculator and its critical modified path, including generated assets and cached client behavior where relevant. Distinguish PR-created, merged, deployed, and verified-live states in the report.
- Do not create a new version for a trivial internal change. Report in compact form: delivered workflow, before/after, tests/browser evidence, PR/merge/live links and unresolved limitations. Never stop just to ask permission for routine in-scope work.
